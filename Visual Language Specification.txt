Visual Language Specification
Matheus Vieira Portfolio — Calm UI System
________________


1. Overall Design Philosophy
Product Personality
This interface speaks in a whisper. It is a Calm UI system designed for a senior product designer's portfolio, prioritizing editorial restraint over visual spectacle. The personality is that of a gallery space: neutral walls, precise lighting, and an absolute conviction that the work should speak louder than the frame.
Design Principles
1. Restraint as Premium Signal The interface never shouts. Every visual element is tuned to the lowest viable intensity. Where typical SaaS interfaces compete for attention, this system withdraws from it. The premium positioning is communicated through what is absent—not what is present.
2. Typography Carries Hierarchy Color is not the primary hierarchy tool. Instead, typographic scale, weight, and font-family shifts create the entire information architecture. Headlines appear in Fraunces (a variable serif with optical size tuning), while all functional UI text uses Instrument Sans. The contrast between serif display and sans-serif utility is the system's signature.
3. Whitespace is Content Negative space is treated as an active design material, not a passive background. Sections breathe with 80px–160px vertical padding. Asymmetric layouts deliberately leave significant portions of the viewport empty. This emptiness directs the eye and creates a meditative reading rhythm.
4. Invisible Structure Grids, borders, and containers exist at the threshold of perception. Borders are hairlines at 10% opacity. Backgrounds are off-whites barely distinguishable from one another. The structural skeleton is felt, not seen.
5. Contextual Disclosure Information is hidden until the user signals intent. Navigation drawers slide from edges. Project details emerge from dots on hover. The contact surface is a modal that scales into view. Nothing is persistently visible unless it serves the immediate context.
Emotional Tone
* Quietly confident: No badges, social proof counters, or trust signals
* Intellectually rigorous: Editorial asymmetry, research documentation, methodical process展示
* Warmly minimal: Warm gray palette avoids the clinical coldness of pure white/black minimalism
* Calm: Reduced visual entropy through monochrome restraint
Product Positioning
This is not a marketing site. It is a credentialing interface—designed to demonstrate taste and judgment to hiring managers, design leads, and collaborators. Every pixel choice must answer: "Does this prove the designer can make difficult restraint decisions?"
Visual Restraint Rules
* No more than one accent color (Sage) per viewport
* No solid black backgrounds (near-black ink on warm off-white only)
* No gradient backgrounds
* No drop shadows on static elements
* No rounded corners larger than 4px on content containers
* No illustrations or decorative graphics beyond the artifact scene
* No animated entrances on page load (calm arrival)
What Should Never Happen Visually
* Never use pure white (#FFFFFF) or pure black (#000000)
* Never use a saturated color other than Sage
* Never use a bold font weight (maximum 600, preferably 400/500)
* Never center-align longform text (left-alignment only)
* Never use a border stronger than 1px at 10% opacity unless signaling an interactive state
* Never fill buttons with solid color (text-only or hairline-outline only)
* Never use more than two font families in a single view
* Never add decorative geometric shapes, patterns, or textures
* Never use all-caps for headlines (label-caps utility only)
* Never exceed 10% border-radius on any element (square-edged editorial aesthetic)

2. Visual Hierarchy
How Hierarchy is Created
This system uses a three-pillar hierarchy: Typography scale → Whitespace grouping → Opacity modulation. Color is the fourth and least-used pillar.
Typography Hierarchy
Display Tier (Fraunces, italic, 300 weight)
* Headlines: 48px–84px, line-height 0.9–1.1
* Used for: Project titles, hero statements, section intros, pull quotes
* Never used for: Body text, navigation, labels, descriptions
Functional Tier (Instrument Sans, 400–500 weight)
* Body: 13px–15px, line-height 1.5–1.6
* Labels: 10px uppercase, letter-spacing 0.1em, weight 500
* Used for: Everything except display headlines
Transition Marker (Fraunces, italic, 120px+, 5% opacity)
* Ghost markers like "Descoberta" and "Síntese" floating behind content
* Non-interactive, purely atmospheric depth cues
Whitespace Hierarchy
* 160px (py-40): Major section breaks between thematic phases
* 80px (py-20): Subsection spacing within a thematic phase
* 40px: Content block internal separation
* 16px–24px: Related element grouping
* 4px–8px: Tight typographic clustering (label + value)
Contrast Hierarchy
* Primary content: Ink (#1A1A1A) at 100% opacity
* Secondary content: Ink at 60%–70% opacity
* Tertiary/meta content: Ink at 30%–40% opacity
* Atmospheric content: Ink at 5%–10% opacity
* Accent content: Sage (#A5B8B1) at 100% opacity
Emphasis Rules
* Strong emphasis: Fraunces italic + scale increase
* Medium emphasis: Opacity reduction of surrounding elements (hover lists reduce non-hovered items to 40%)
* Weak emphasis: Underline animation (scaleX transform from center)
* No emphasis: Standard body text at 70% opacity
Primary vs. Secondary Information
Primary information is always left-aligned and positioned in the optical center-left (not geometric center). Secondary information is either:
1. Offset to the right in an asymmetric grid
2. Placed below with increased spacing
3. Revealed only on interaction (tooltip, drawer expansion)
How Actions Compete
Actions do not compete visually. They are deliberately quiet:
* Navigation links use animated hairline underlines
* Buttons are text-only with optional arrow icon
* The only persistent interactive accent is the Sage color used sparingly for section labels or success states
* All interactive elements share the same hover treatment: opacity shift to 50% or underline reveal
Progressive Disclosure Principles
* Level 1 (Surface): Brand, headline, three project dots, three nav links
* Level 2 (Hover): Project titles and descriptions emerge from dots; nav underlines appear
* Level 3 (Click): Full project case study overlays viewport; drawers slide from edges; modals scale in
* Level 4 (Scroll): Secondary research, personas, and methodology revealed through longform vertical reading
* Nothing at Level 2+ is visible without user intent

3. Spacing System
Base Grid
The underlying grid is 8px-based (Tailwind default) but used selectively. The effective spatial rhythm is closer to a 16px grid for macro layout and 4px for micro typography alignment.

	Page Gutters
* Desktop: 60px–80px horizontal padding (px-15 to px-20)
* Tablet: 40px horizontal padding
* Mobile: 24px horizontal padding (px-6)
* Content max-width: 900px–1400px depending on section type
* Case study content: max-width 900px centered (narrow reading measure)
* Homepage artifact: max-width 1200px
Section Spacing
* Between major case study sections: py-32 (128px)
* Between subsections within a phase: py-16 to py-24 (64px–96px)
* Hero sections receive extra top padding: pt-24 to account for fixed header
* Footer spacing: py-40 (160px) to create a definitive ending
Card Spacing
* Internal padding: p-8 (32px) to p-10 (40px)
* Border: hairline 1px at 10% opacity
* No border-radius on case study cards (0px) or minimal 2px
* Stat cards use border: 1px solid var(--ink) for stronger emphasis
Internal Component Spacing
* Navigation link separation: 40px gap
* Header internal spacing: 4px between brand name and subtitle
* Project row spacing: 30px vertical padding with hairline separator
* Meta grid: 4-column layout with generous internal spacing
Density Philosophy
Relaxed density is the default. Case study pages use a narrow measure (max-width 900px) with generous line-height. Dashboard-style metrics grids are the densest elements, but even these use 40px+ internal padding.
Breathing Room Rules
1. Never place two distinct thematic sections closer than 128px vertically
2. Always maintain at least 40px between a label-caps header and its content
3. Images must have at least 24px separation from surrounding text
4. Sticky side labels require at least 80px horizontal offset from main content
5. The artifact scene on the homepage must have at least 80px margin from viewport edges

1. CORE DESIGN THESIS
The portfolio should feel like:
a designer's personal artifact that happens to be a website, rather than a website decorated to look personal.
The central principle is:
If an element only exists to make the website look cool, remove it.
Every unusual interaction must either:
communicate information,
reveal content,
establish navigation,
create a meaningful relationship between the physical and digital,
or materially improve the experience.
Avoid interaction for interaction's sake.
The site should feel authored, restrained, tactile, intelligent, slightly unexpected, and human.
It should NOT feel like:
a generic SaaS portfolio
a Framer template
a Webflow awards-site clone
a brutalist developer portfolio
a "creative agency" website

a collection of animation experiments
a design-system showcase disguised as a portfolio
The personality should come from the relationship between content, typography, photography, physical artifacts, and interaction, not from visual effects.

### Imagem vs. texto
Modelo híbrido: imagem grande fazendo o trabalho visual (wireframes, telas, diagramas, fotos reais),
texto sempre como HTML de verdade por cima ou ao lado — nunca embutido no pixel da imagem.
Motivo: texto embutido em imagem não é selecionável, não é lido por leitor de tela, não é indexado,
e em mobile vira pinch-zoom. O conteúdo já existe separado (texto e imagem em camadas distintas no Figma).
### Blocos do sistema (o "kit de peças" que precisa existir)
1. Hero do case — eyebrow, headline, subhead, metadados (papel, duração, ferramentas), resultado
principal em destaque
2. Bloco de evidência/números — 40%→0%, 18 entrevistas, 247 respostas, 5 rounds de teste,
12h de campo, 23 pontos de atrito
3. Bloco de contexto — o problema mapeado (service blueprint: estacionamento → corredor →
checkout → saída)
4. Bloco de research — fotos de campo reais, metodologia (double diamond), lista numerada de
pain points (7), personas reais (3)
5. Bloco de benchmark/competitive — comparação com concorrentes reais (Zara, Amazon Go, Carrefour,
Extra, Walmart) por critério
6. Bloco de evolução — a mesma tela em fidelidades diferentes (papel → hi-fi → final), mostrando
o pulo consciente do mid-fi
7. Bloco de solução (repetível ×5 no Square, mas precisa suportar N) — nome, pain point que resolve,
tag de dispositivo real (app/totem), telas reais
8. Bloco de impacto/next steps
9. Footer do case (voltar pra home, próximo case)
Cada bloco precisa ser desenhado como componente com variações de tamanho de conteúdo
(e se o case futuro tiver só 2 soluções? só 1 persona?) — não como página fixa.
### Dualidade app/totem
Enquanto existir esse padrão nos cases, o bloco de solução precisa ter um jeito visual padrão de
marcar "isso roda no app" vs "isso roda no totem" — não uma tag de texto solta remontada do zero
a cada case novo.

AUDIT DE CONTEÚDO — SEÇÃO POR SEÇÃO
1. Hero
Veredito: MANTÉM como está
Motivo: Já funciona para os dois públicos. O recrutador escaneia título + metadados + impacto em 3 segundos e sai com a prova de rigor (6 meses, retail tech, -40%). O designer entra sabendo do que se trata. Não tocar.
________________


2. Contexto do Projeto
Veredito: CONDENSA
Motivo: O recrutador não precisa de história corporativa. O designer precisa de just enough context para entender o território. Reduzir a 2 frases curtas — o que é o Square Self-Checkout e por que ele existia. Qualquer coisa sobre "expansão do Square para POS físico" ou histórico da empresa → corta.
________________


3. Objetivos
Veredito: CONDENSA em bullets, MOVE detalhamento para secundário
Motivo: Objetivos de negócio são previsíveis (reduzir tempo, reduzir erro, aumentar NPS). No fluxo principal, mantenha 3 bullets de uma linha cada. Se houver objetivos técnicos ou de negócio complexos (OKRs, métricas de baseline), link "Ver objetivos completos" que expande ou leva para um documento à parte. Não ocupa scroll precioso com parágrafo de objetivo.
________________


4. Processo/Metodologia
Veredito: MOVE para camada secundária, substituir no fluxo principal por "Rigor em números"
Motivo: O diagrama de metodologia é research theater — todo designer já viu double-diamond. O que prova rigor são os números brutos: 18 entrevistas, 247 respostas de survey, 5 rodadas de teste, 2 iterações. Crie um bloco tipográfico horizontal (4 colunas de dados) no início da seção de pesquisa. O diagrama completo de metodologia vira um link "Ver processo completo" ou expande em um drawer/overlay. Recrutador vê os números e fica satisfeito; designer clica se quiser o arcabouço.
________________


5. Pesquisa de Usuário
Veredito: CONDENSA no fluxo principal, MOVE análise completa para secundário
Motivo: 247 respostas de survey geram dezenas de insights. No fluxo principal, mantenha 3-4 dados que chocam (ex: "73% abandonavam o fluxo no terceiro toque", "Categoria 'Frutas' era o maior gargalo"). Use citações verbatim de 1-2 usuários como punchlines. Todo o restante — gráficos de survey completos, tabulação cruzada, análise estatística → expandível ou link externo. Isso prova que você fez a pesquisa sem entediar quem está scrollando.
________________


6. Exploração de Campo
Veredito: CONDENSA radicalmente
Motivo: Observação de campo é poderosa, mas fotos de supermercado falam mais que texto. Mantenha no fluxo principal: 1 foto full-bleed com 1 legenda de 1 linha (ex: "Ação: cliente segura maçã em uma mão e tenta navegar com a outra"). Todo o roteiro de campo, horários, notas etnográficas completas → galeria secundária ou link. Corte narrações do tipo "Chegamos às 9h no dia...".
________________


7. Jornada/Pain Points
Veredito: MANTÉM resumida no fluxo principal, com opção de expandir
Motivo: Mapa de jornada é um dos poucos diagramas que funciona como imagem — recrutadores entendem visualmente onde está o problema. Mantenha o mapa simplificado (3-4 estágios, pain points em destaque). A versão completa (12 touchpoints, emoções, oportunidades, quotes) → expande em modal/drawer ou link. É um bom ponto de transição entre "problema" e "solução".
________________


8. Personas
Veredito: CORTA do fluxo principal, MOVE para secundário (ou reduz a 1 linha)
Motivo: Em 2024, personas completas (nome, idade, foto, bio, frustrações, metas) são peso morto no scroll. Recrutadores pulam. Designers sabem que são síntese. Se quiser manter o rigor, substitua no fluxo principal por "Arquétipos de usuário" — 2 linhas de texto por arquétipo (ex: "Comprador apressado: sabe o que quer, tolerância de erro zero"). Se alguém quiser ver as personas completas com foto, clica para expandir. Isso libera espaço enorme.
________________


9. JTBD (Jobs to Be Done)
Veredito: MOVE para camada secundária, CONDENSA no fluxo principal para 3 bullets
Motivo: JTBD é framework valioso para designers, mas visualmente é texto denso e abstrato. No fluxo principal, mantenha 3 jobs em bullets curtos: "Quando estou no checkout, quero identificar meu item rapidamente para não segurar a fila". O framework completo (jobs principais, relacionais, emocionais, outcomes esperados) → documento secundário. Recrutador vê que você usou JTBD; designer acessa o detalhe.
________________


10. Design & Prototipação
Veredito: CONDENSA no fluxo, MOVE iterações completas para galeria secundária
Motivo: O arco do processo (Crazy 8s → papel → digital → alta fidelidade) é uma prova de craft. No fluxo principal, mostre 1 imagem de cada estágio (4 imagens em grid horizontal) com 1 frase de transição. Detalhes de cada rodada de Crazy 8s, todas as variações de sketch, notas de handoff completas → galeria secundária. Recrutador vê que você desenha à mão e itera; designer clica para ver o processo bruto.
________________


11. Teste Round 1
Veredito: MANTÉM resumida no fluxo principal, expandir para detalhes
Motivo: Teste de usabilidade é prova de rigor que recrutadores entendem ("testamos com 5 usuários, descobrimos 3 bloqueios, corrigimos 2 antes do handoff"). No fluxo principal: dados duros + 1 foto do teste. O plano de teste completo, script, notas por participante, heatmaps → secundário. Isso mantém a credibilidade sem carregar o scroll.
________________


12. As 5 Soluções
Veredito: MANTÉM como bloco principal
Motivo: Este é o core do case — é onde os dois públicos mais se beneficiam. Recrutador vê que você resolveu problemas concretos; designer vê raciocínio de interação. Cada solução deve seguir o ritmo: Problema (1 frase) + Citação (1 linha, itálico) + Solução (2-3 frases) + Mockup. Nada disso pode ser cortado do fluxo principal. É o único bloco que merece volume real.
________________


13. Next Steps
Veredito: CONDENSA para 1-2 frases ou CORTA
Motivo: Next steps é quase sempre lido por ninguém. Se for incluir, faça 1 parágrafo curto sobre o que aconteceu depois ("Sistema implementado em X lojas piloto"). Se for apenas "futuras melhorias", corte. Recrutadores não contratam por roadmap; designers não aprendem processo com next steps.
________________


14. Footer
Veredito: MANTÉM
Motivo: "Próximo Projeto" já está no sistema. Funciona como quebra de seção e transição de narrativa. Manter.

EXPLORAÇÃO VISUAL A: DISTINÇÃO APP VS TOTEM
Proposta: Sistema de "Marcação por proporção"
Nada de ícones de celular ou monitor. A própria razão de aspecto do container é o sinalizador, reforçada por uma legenda tipográfica minimal:
App (393×852)
      * Container com max-width de 280px, cantos levemente arredondados (6px), centralizado ou alinhado à esquerda da coluna de texto.
      * Acima do container: uma linha em caps, 10px, cor sage:
MOBILE — 393 × 852
      * O container nunca toca as bordas da coluna. Flutua com breathing room.
Totem/Kiosk (1920×1080)
         * Container full-width da coluna de conteúdo (ou 100% do grid de 7fr), cantos quadrados (2px).
         * Legenda acima:
TOTEM — 1920 × 1080
         * A proporção 16:9 já comunica "tela grande" sem nenhum desenho.
App + Totem (ambos)
            * Layout split: container do app à esquerda (30% largura) e do totem à direita (70%), separados por 1px hairline vertical em 10% de opacidade.
            * Legenda acima de cada metade, respectivamente.
            * Ou, se a solução afeta os dois mas só há um mockup: legenda única APP • TOTEM acima do mockup principal.
Elemento adicional (opcional, mas consistente):
Se a solução é só para operadores vs só para clientes, use uma palavra-chave na mesma linha da legenda:
APP — 393 × 852 — Cliente ou TOTEM — 1920 × 1080 — Operador
Isso cria um padrão tipográfico zero ruído, 100% repetível, que educa o leitor sobre onde cada solução vive sem nunca quebrar a calma visual da página.
________________


EXPLORAÇÃO VISUAL B: RITMO DE IMAGENS E DIAGRAMAS
Proposta: 3 velocidades visuais
Para manter a filosofia Benji (espaço fala mais que decoração), organize as 15+ imagens em três categorias de tratamento:
1. Full-bleed (quebra de galeria)
            * Usar para: Hero image, 1 foto de campo, comparação Antes/Depois final.
            * Regra: toca as bordas da viewport, mas com padding vertical enorme (160-200px) antes e depois. A imagem respira sozinha; nunca encosta em texto.
2. Contained na coluna editorial (max-width 700-800px)
            * Usar para: Screenshots de solução (dentro dos device frames da Exploração A), citações de pesquisa com gráfico pequeno, foto do protótipo de papel.
            * Regra: vive dentro do grid 7fr da coluna direita, nunca escapa. Mantém o ritmo de leitura contínua.
3. Redesenho tipográfico (zero imagem importada)
            * Usar para: Mapa de jornada simplificado, fluxo de metodologia, arquétipos de usuário.
            * Regra: em vez de importar um PNG do Miro/Figma com cores, setas e caixas, redesenhe usando o próprio sistema do site:
            * Fraunces 300 para números de estágio (01, 02, 03...)
            * Instrument Sans para labels
            * Hairlines de 1px em var(--border) para conectar
            * Stone background para caixas de estágio, sem sombra, sem border-radius agressivo
            * Resultado: o diagrama parece nativo da página, não uma imagem colada. Resolve o problema de "imagem solta quebrando a calma".
Ritmo de alternância sugerido:
[Texto editorial] → [Imagem contained: solução App] → [Texto] → [Full-bleed: foto de campo] → [Texto] → [Diagrama tipográfico: jornada] → [Texto] → [Imagem contained: solução Totem] → [Full-bleed: comparação antes/depois] → ...
A regra geral: nunca coloque duas imagens/diagramas seguidos sem texto entre elas. Benji usa o texto como descanso visual entre impactos. Duas imagens seguidas competem por atenção e cansam.
Galeria de processo (Crazy 8s, sketches):
Mantenha o grid de 3 colunas já existente no sistema, mas com gap menor (12px) e imagens quadradas. Isso cria um bloco denso que contrasta com o respiro editorial ao redor — o contraste é o que torna a galeria especial, não o tamanho.
________________


EXPLORAÇÃO VISUAL C: NAVEGAÇÃO EM ROLAGEM LONGA SEM CHROME
Proposta: "Marcos de fundo + índice sob demanda"
1. Marcos tipográficos entre grandes blocos (padrão principal) Entre cada seção principal (Hero → Contexto → Pesquisa → Jornada → Soluções → Footer), insira um marco de seção:
            * Um úmero romano ou palavra-chave em Fraunces 300, ~96-120px, cor em 5% de opacidade do ink, posicionado como uma camada de fundo (z-index baixo, pode ser parcialmente coberto pelo conteúdo ou flutuar no espaço vazio entre blocos).
            * Exemplos:
I. O Desafio
II. Pesquisa
III. Solução
(Ou em português: Descoberta, Síntese, Design)
            * Não é um divisor ativo; é um sinal de orientação subliminar. Quem está scrollando rápido nota a mudança de palavra; quem está lendo não é interrompido.
2. Índice sob demanda (controle discreto)
               * Um único elemento fixo: § (símbolo de seção) em 10px caps, posicionado no bottom-left, 40px de margem. Opacidade 30% por padrão.
               * Ao passar o mouse (ou tocar, no mobile), expande para uma lista vertical de 5-6 marcos principais (Hero, Pesquisa, Jornada, Soluções, Resultado, Próximo) em Instrument Sans 12px, alinhados à esquerda.
               * Clicar num item scrolla suavemente para a âncora correspondente.
               * Não é uma sidebar, não é um header sticky, não é uma TOC visível o tempo todo. É um atalho escondido em plain sight — recrutadores nunca precisam dele; designers agradecem.
3. (Alternativa ainda mais mínima) Se até o "§" parece chrome demais, elimine-o completamente. Use apenas os marcos tipográficos de fundo + um comportamento nativo: o header do site (que já é fixo) pode ter seus links de navegação (Projetos / Sobre / Contato) acompanhados de um link contextual nesta página: ↑ Topo. Nada mais.

Recomendação final:
Adote o marco tipográfico de fundo + índice via § como padrão. Ele mantém a filosofia da homepage (zero chrome, espaço como hierarquia) enquanto torna uma rolagem de 6.000+ px navegável sem perda de orientação.
Esse audit ficou muito bom — a lógica de camada principal/secundária é exatamente o tipo de solução que resolve a tensão real (conteúdo genuinamente longo vs. filosofia de restrição) sem simplesmente cortar substância. Antes de você aprovar e pedir pro variant.com prototipar, tem um ponto estratégico que eu levantaria com força, e alguns ajustes menores.
O ponto que mais me preocupa: o corte pode ser agressivo demais pro seu contexto específico. A lógica do audit ("recrutador escaneia, designer clica se quiser detalhe") funciona muito bem pra alguém com portfólio de trabalhos reais em empresas — a prova de competência vem do outcome no mercado. Mas você é júnior em transição de carreira, sem esse histórico ainda: o rigor do processo (metodologia, personas, JTBD, card sorting) NÃO é decoração no seu caso — é a principal prova de que você sabe fazer UX de verdade, porque é o que substitui a experiência de mercado que você ainda não tem. Se metodologia, personas e JTBD ficarem só como "clique pra expandir" e a maioria dos recrutadores nunca clicar (o que é o comportamento típico), seu case corre o risco de parecer "só visual bonito" pra quem não se aprofunda — o oposto do que você precisa provar. Eu manteria a estrutura de camadas proposta, mas tornaria a camada principal um pouco mais substantiva nesses blocos específicos (metodologia, personas, JTBD) — não parágrafos longos, mas também não só uma linha solta — o suficiente pra alguém que só lê o fluxo principal ainda sair convencido do seu rigor, mesmo sem clicar em nada.
Complexidade de implementação das camadas secundárias. O audit criou 7 pontos de expansão diferentes espalhados pela página (metodologia completa, survey completo, notas de campo, personas completas, JTBD framework, sketches, plano de teste, roadmap). Cada um provavelmente vira um componente/interação própria pra construir. Eu pediria pro variant.com considerar consolidar isso em UM destino só — algo como "Ver o processo de pesquisa completo" linkado uma vez perto do início, levando a uma página/seção-âncora única com todo o material aprofundado organizado por sub-título — em vez de 7 mecanismos de expansão diferentes no meio do scroll. Mais simples de construir, mais simples de navegar, e ainda cumpre o objetivo de não inchar o fluxo principal.
Dois pontos de fidelidade ao conteúdo real, pra não fabricar sem querer: as citações verbatim sugeridas ("73% abandonavam no terceiro toque" etc.) precisam ser as reais do seu survey/entrevistas, não frases de exemplo que o variant.com inventou pra ilustrar o padrão — confirma isso antes de aprovar o texto final. E a tag "Operador" no sistema de marcação de dispositivo (Exploração A) só faz sentido se existir de fato uma tela voltada pra funcionário/operador no case — pelo que você descreveu, a assistência da equipe na verificação de idade é uma opção que o CLIENTE escolhe, não uma interface que o operador usa. Eu tiraria esse rótulo a menos que exista uma tela real de operador.
Exploração A (proporção como sinalizador de dispositivo): aprovo sem ressalvas. É elegante, zero decoração, e as dimensões reais (393×852, 1920×1080) reforçam a voz factual que vocês já estabeleceram. Ótima solução.
Exploração B (3 velocidades de imagem + diagramas redesenhados nativamente): aprovo, com uma ressalva prática. Redesenhar o mapa de jornada e o fluxo de metodologia como diagramas tipográficos nativos (em vez de imagem importada do Miro/Figma) é a escolha certa pra manter a calma visual — mas é trabalho de produção extra, não só decisão de layout: alguém (você ou eu, no Claude Code) vai ter que recriar esses diagramas do zero no sistema. Vale confirmar que topa esse esforço antes de travar essa direção.
Exploração C (marcos tipográficos + índice via "§"): aprovo os marcos, testaria o "§" com cautela. Os marcos de fundo (palavra grande, baixa opacidade) são puro benji — mantenha. Mas o símbolo "§" no canto como affordance de índice é sutil a ponto de arriscar ser invisível pra maioria das pessoas — a maior parte dos visitantes não vai saber o que aquele símbolo significa nem que passar o mouse ali revela algo, e em touch (celular) não existe hover, então precisaria virar tap, com um alvo de toque maior do que 10px pra ser acessível. Matheus Vieira Portfolio — Calm UI System
________________


1. Overall Design Philosophy
Product Personality
This interface speaks in a whisper. It is a Calm UI system designed for a senior product designer's portfolio, prioritizing editorial restraint over visual spectacle. The personality is that of a gallery space: neutral walls, precise lighting, and an absolute conviction that the work should speak louder than the frame.
Design Principles
1. Restraint as Premium Signal The interface never shouts. Every visual element is tuned to the lowest viable intensity. Where typical SaaS interfaces compete for attention, this system withdraws from it. The premium positioning is communicated through what is absent—not what is present.
2. Typography Carries Hierarchy Color is not the primary hierarchy tool. Instead, typographic scale, weight, and font-family shifts create the entire information architecture. Headlines appear in Fraunces (a variable serif with optical size tuning), while all functional UI text uses Instrument Sans. The contrast between serif display and sans-serif utility is the system's signature.
3. Whitespace is Content Negative space is treated as an active design material, not a passive background. Sections breathe with 80px–160px vertical padding. Asymmetric layouts deliberately leave significant portions of the viewport empty. This emptiness directs the eye and creates a meditative reading rhythm.
4. Invisible Structure Grids, borders, and containers exist at the threshold of perception. Borders are hairlines at 10% opacity. Backgrounds are off-whites barely distinguishable from one another. The structural skeleton is felt, not seen.
5. Contextual Disclosure Information is hidden until the user signals intent. Navigation drawers slide from edges. Project details emerge from dots on hover. The contact surface is a modal that scales into view. Nothing is persistently visible unless it serves the immediate context.
Emotional Tone
                  * Quietly confident: No badges, social proof counters, or trust signals
                  * Intellectually rigorous: Editorial asymmetry, research documentation, methodical process展示
                  * Warmly minimal: Warm gray palette avoids the clinical coldness of pure white/black minimalism
                  * Calm: Reduced visual entropy through monochrome restraint
Product Positioning
This is not a marketing site. It is a credentialing interface—designed to demonstrate taste and judgment to hiring managers, design leads, and collaborators. Every pixel choice must answer: "Does this prove the designer can make difficult restraint decisions?"
Visual Restraint Rules
                  * No more than one accent color (Sage) per viewport
                  * No solid black backgrounds (near-black ink on warm off-white only)
                  * No gradient backgrounds
                  * No drop shadows on static elements
                  * No rounded corners larger than 4px on content containers
                  * No illustrations or decorative graphics beyond the artifact scene
                  * No animated entrances on page load (calm arrival)
What Should Never Happen Visually
                  * Never use pure white (#FFFFFF) or pure black (#000000)
                  * Never use a saturated color other than Sage
                  * Never use a bold font weight (maximum 600, preferably 400/500)
                  * Never center-align longform text (left-alignment only)
                  * Never use a border stronger than 1px at 10% opacity unless signaling an interactive state
                  * Never fill buttons with solid color (text-only or hairline-outline only)
                  * Never use more than two font families in a single view
                  * Never add decorative geometric shapes, patterns, or textures
                  * Never use all-caps for headlines (label-caps utility only)
                  * Never exceed 10% border-radius on any element (square-edged editorial aesthetic)

2. Visual Hierarchy
How Hierarchy is Created
This system uses a three-pillar hierarchy: Typography scale → Whitespace grouping → Opacity modulation. Color is the fourth and least-used pillar.
Typography Hierarchy
Display Tier (Fraunces, italic, 300 weight)
                  * Headlines: 48px–84px, line-height 0.9–1.1
                  * Used for: Project titles, hero statements, section intros, pull quotes
                  * Never used for: Body text, navigation, labels, descriptions
Functional Tier (Instrument Sans, 400–500 weight)
                  * Body: 13px–15px, line-height 1.5–1.6
                  * Labels: 10px uppercase, letter-spacing 0.1em, weight 500
                  * Used for: Everything except display headlines
Transition Marker (Fraunces, italic, 120px+, 5% opacity)
                  * Ghost markers like "Descoberta" and "Síntese" floating behind content
                  * Non-interactive, purely atmospheric depth cues
Whitespace Hierarchy
                  * 160px (py-40): Major section breaks between thematic phases
                  * 80px (py-20): Subsection spacing within a thematic phase
                  * 40px: Content block internal separation
                  * 16px–24px: Related element grouping
                  * 4px–8px: Tight typographic clustering (label + value)
Contrast Hierarchy
                  * Primary content: Ink (#1A1A1A) at 100% opacity
                  * Secondary content: Ink at 60%–70% opacity
                  * Tertiary/meta content: Ink at 30%–40% opacity
                  * Atmospheric content: Ink at 5%–10% opacity
                  * Accent content: Sage (#A5B8B1) at 100% opacity
Emphasis Rules
                  * Strong emphasis: Fraunces italic + scale increase
                  * Medium emphasis: Opacity reduction of surrounding elements (hover lists reduce non-hovered items to 40%)
                  * Weak emphasis: Underline animation (scaleX transform from center)
                  * No emphasis: Standard body text at 70% opacity
Primary vs. Secondary Information
Primary information is always left-aligned and positioned in the optical center-left (not geometric center). Secondary information is either:
                  1. Offset to the right in an asymmetric grid
                  2. Placed below with increased spacing
                  3. Revealed only on interaction (tooltip, drawer expansion)
How Actions Compete
Actions do not compete visually. They are deliberately quiet:
                  * Navigation links use animated hairline underlines
                  * Buttons are text-only with optional arrow icon
                  * The only persistent interactive accent is the Sage color used sparingly for section labels or success states
                  * All interactive elements share the same hover treatment: opacity shift to 50% or underline reveal
Progressive Disclosure Principles
                  * Level 1 (Surface): Brand, headline, three project dots, three nav links
                  * Level 2 (Hover): Project titles and descriptions emerge from dots; nav underlines appear
                  * Level 3 (Click): Full project case study overlays viewport; drawers slide from edges; modals scale in
                  * Level 4 (Scroll): Secondary research, personas, and methodology revealed through longform vertical reading
                  * Nothing at Level 2+ is visible without user intent

4. Layout Principles
Page Width
                  * Full-bleed sections: Backgrounds and atmospheric elements extend to viewport edges
                  * Contained content: max-width 1400px (7xl) for standard sections, 900px for case study reading
                  * Centered containers: Content blocks are centered horizontally with auto margins
Container Sizing
                  * Homepage artifact scene: max-width 1200px, aspect-ratio 16/9 (desktop), 4/5 (mobile)
                  * Case study hero: Full viewport width, 80vh height
                  * Reading container: max-width 900px for longform text
                  * Drawer/modal: 520px (about), 360px (contact), 600px (projects)
Alignment Rules
                  * Primary axis: Left-aligned text is the universal default
                  * Asymmetric grid: Case studies use 12-column grids with intentional imbalance (e.g., label in col-span-3, content in col-span-7 offset by col-start-5)
                  * Centered exceptions: Hero headlines may be centered only when explicitly declarative. Metric grids and process steps are centered within their containers
                  * Right alignment: Used exclusively for navigation and close buttons
Responsive Behavior
Desktop (>1024px)
                  * Dual header: brand left, nav right
                  * 12-column asymmetric grids
                  * Side labels visible (sticky positioning)
                  * Full artifact scene 16:9
Tablet (768px–1024px)
                  * Drawer widths reduce to 480px
                  * Grids collapse to 2-column where appropriate
                  * Artifact scene adjusts to 16:10
Mobile (<768px)
                  * Header stacks vertically: Brand name / subtitle / headline / horizontal nav
                  * Navigation links become horizontal with dot separators (·)
                  * Artifact scene becomes 4:5 portrait
                  * 12-column grids collapse to single column
                  * Side labels disappear or inline above content
                  * Sticky positioning disabled for side labels
                  * Dots enlarge to 20px with visible labels
Stacking Rules
                  * Z-index hierarchy:
                  * Base content: z-0 to z-10
                  * Sticky headers: z-50
                  * Drawers/overlays: z-200–z-300
                  * Modals: z-2000
                  * Fixed nav elements: z-[60] to z-[1000]
Visual Rhythm
The reading rhythm alternates between dense research phases and breathing moments:
                  1. Dense content block (metrics, personas, tables)
                  2. Ghost marker / atmospheric break (py-24 with large faint text)
                  3. Dense content block
                  4. Full-bleed image or divider
                  5. Dense content block
This alternation prevents visual fatigue during long case studies.
Reading Flow
                  * F-pattern variant: Labels anchor the left edge; content flows from left-center
                  * Z-pattern: Used in hero sections (brand top-left → nav top-right → headline bottom-left)
                  * Center-out: Modals and contact forms emerge from center; the user's attention collapses inward
Content Grouping
                  * Related content is grouped by proximity (generous internal padding) rather than visible borders
                  * When borders are used, they are hairline and full-width (section separators)
                  * Cards and tables are the only elements that use enclosed borders

6. Color Language
Semantic Color Usage
Page Background (#F5F2F0)
                  * Warm off-white with a hint of rose/beige
                  * Prevents the clinical sterility of pure white
                  * Used for: Global body background, modal backgrounds, drawer backgrounds
                  * Never use pure white (#FFFFFF) — this warm tone is essential to the emotional warmth of the system
Ink (#1A1A1A)
                  * Near-black with slight warmth
                  * Primary text, borders (at various opacities), interactive elements
                  * Used at 100% for primary text, 60% for secondary, 30%–40% for tertiary, 10% for hairlines, 5% for ghost markers
Stone (#E6E2DF)
                  * Warm mid-gray
                  * Used for: Image placeholders, device mockup backgrounds, secondary surfaces, blockquote backgrounds
                  * Creates subtle surface layering without visual noise
                  * Never used for text (insufficient contrast)
Sage (#A5B8B1)
                  * Muted blue-green, desaturated
                  * The only accent color in the entire system
                  * Used for: Section label prefixes, pull quote borders, success states, subtle hover indicators, dot ring animations
                  * Never used for: Large fills, buttons, backgrounds (except 20% opacity overlays)
Grayscale Philosophy
The system is effectively monochrome + one accent. All text lives on a grayscale spectrum of opacity rather than using multiple gray hex values. This creates a more cohesive, atmospheric depth than multi-gray palettes.
Why opacity over hex grays?
                  * Creates smoother transitions between hierarchy levels
                  * Allows elements to recede without changing their base hue
                  * Maintains color consistency across all text
                  * Enables subtle hover states simply by adjusting opacity
Accent Colors
                  * Sage is the sole accent
                  * Usage cap: No more than 10% of viewport area should contain Sage at any time
                  * Typical placements: Section label prefix ("Contexto"), quote border, interactive ring animation, hover underline on special links
Interactive Colors
                  * Default: Ink at 100%
                  * Hover: Opacity 50% OR underline reveal
                  * Active/Selected: Ink at 100% with visible underline
                  * Focus: Same as hover (no outline rings; the system avoids focus outlines in favor of subtle state changes)
Disabled Colors
                  * Disabled elements: Ink at 30% opacity, no pointer-events
                  * No special disabled background color
Background Strategy
                  * Base layer: Page-bg (#F5F2F0)
                  * Content layer: Transparent (inherits base)
                  * Card/surface layer: Stone (#E6E2DF) or transparent with hairline border
                  * Overlay layer: Page-bg at 92%–98% opacity with backdrop-filter blur(10px)
                  * Dark inversion: Rare; only used in dramatic section transitions (e.g., "Evolução do Sistema" section with bg-ink and text-page-bg)
Surface Hierarchy
                  1. Base: Page-bg (global)
                  2. Elevated: Stone (placeholder blocks, inactive device frames)
                  3. Floating: Overlay-bg (rgba(245,242,240,0.98))
                  4. Overlay: Semi-transparent Page-bg with blur
Border Colors
                  * Standard: rgba(26, 26, 26, 0.1) — hairline, barely visible
                  * Strong: var(--ink) solid 1px — used for stat cards and emphasis containers
                  * Accent: var(--sage) — used for pull quote left borders, active section indicators
Emphasis Rules
                  * High emphasis: Scale + Fraunces italic + full ink opacity
                  * Medium emphasis: Instrument Sans + 18px + full ink opacity
                  * Low emphasis: Label-caps + 10px uppercase + sage or 40% opacity
                  * Atmospheric: Ghost markers + 120px + 5% opacity
When Color SHOULD Be Used
                  * Section labels to orient the reader (Sage)
                  * Pull quote borders to signal editorial content (Sage)
                  * Hover ring animations on interactive dots (Sage)
                  * Error/success metrics (Sage for positive, muted red for pain points)
When Color SHOULD NEVER Be Used
                  * Never for primary buttons (text-only)
                  * Never for large backgrounds (avoid color blocks)
                  * Never for navigation (text-only, ink color)
                  * Never for decorative elements (no colored shapes, icons, or illustrations)
                  * Never for body text emphasis (use weight or opacity, not color)

8. Elevation System
Shadows
This system avoids drop shadows as a general rule. Depth is communicated through:
                  * Scale transforms
                  * Blur overlays
                  * Opacity layers
                  * Spatial displacement (sliding drawers, scaling modals)
When shadows are used (extremely rare):
                  * Contact modal: box-shadow: 0 40px 80px rgba(0,0,0,0.1) — large, diffuse, low opacity
                  * Navigation switcher: box-shadow: 0 4px 20px rgba(0,0,0,0.1)
Surface Hierarchy
Elevation is achieved through layering semitransparent surfaces rather than shadows:
                  1. Base layer: Page-bg, fully opaque
                  2. Content layer: Transparent, sits on base
                  3. Overlay layer: rgba(245,242,240,0.92) with backdrop-filter: blur(10px) — used for drawers and modals
                  4. Fixed header layer: bg-page-bg/80 with backdrop-filter: blur(12px) — floats above scrolling content
Floating Components
                  * Fixed header: Semi-transparent with backdrop blur
                  * Back-to-top / section navigation: Fixed bottom-left, pill shape
                  * Modals: Centered, scale-in animation, semi-transparent background
                  * Drawers: Slide from left/right, semi-transparent background
Layering
                  * Background: z-0
                  * Content: z-10
                  * Sticky side labels: z-10 (within flow)
                  * Fixed header: z-50
                  * Fixed nav controls: z-[60]
                  * Drawers: z-200
                  * Case overlays: z-300
                  * Modals: z-2000
Overlays
Overlays use the same base color as the page background (Page-bg) at 92%–98% opacity with a 10px blur. This creates a frosted-glass effect that maintains the warm color temperature while signaling a layer separation.
Never use:
                  * Dark overlays (unless specifically inverting for dramatic section)
                  * Black backdrops with opacity
                  * Backdrop blur greater than 20px
Depth Philosophy
Depth should be felt, not seen. The system rejects the Material Design elevation model (shadows indicating height). Instead:
                  * Sliding: Drawers physically move from off-canvas (spatial depth)
                  * Scaling: Modals grow from 0.95→1.0 (proximity depth)
                  * Blurring: Background content blurs when overlay opens (focus depth)
                  * Brightness: Background dims to brightness(0.85) when overlay opens (atmospheric depth)

9. Borders & Dividers
Border Strength
The system uses a single border language: 1px solid at low opacity.
                  * Hairline: rgba(26,26,26,0.1) — universal default for all containers, cards, section dividers
                  * Standard: rgba(26,26,26,0.2) — rarely used
                  * Strong: var(--ink) solid — used for stat cards and emphasis elements
                  * Accent: var(--sage) — used for pull quote left borders (2px)
Divider Usage
                  * Section separation: Full-width hairline border-top or border-bottom on section containers
                  * Content separation: Hairline between list items (project rows, table rows)
                  * Internal separation: Hairline inside grids (metric meta grid)
                  * Card enclosure: Hairline on all four sides of cards
Separators
                  * Horizontal rules are preferred over vertical rules
                  * When vertical rules are needed (e.g., JTBD table), they are implicit via column gutters rather than drawn lines
                  * The only drawn vertical element is the pull quote left border (2px solid Sage)
Structural Lines
                  * Invisible structure: Most layout separation is achieved through whitespace, not lines
                  * Visible structure: Lines appear only when content requires explicit grouping (tables, multi-step processes, metric grids)
                  * Process dividers: In journey maps (Jornada do Usuário), thin horizontal lines connect steps at 10% opacity
Invisible Structure
The system prefers whitespace-defined groups over line-defined groups. Two content blocks separated by 80px+ are understood as distinct without a dividing line. Lines are used only when:
                  1. Content density is high (tables, personas grid)
                  2. Items are chronologically sequential (roadmap, process steps)
                  3. Content must be scanned rapidly (metrics, feature lists)

10. Iconography
Icon Family
The system uses no icon library. Icons are:
                  * Single Unicode characters (→, ←, ↑, /, ✕)
                  * Inline SVG for specific UI needs (hamburger menu icon as SVG lines)
                  * Text characters styled with the system's fonts
Weights
All iconographic elements inherit the typographic weight:
                  * Arrows and symbols use the font-weight of their surrounding text
                  * No bold icons against light text
                  * No filled icon shapes (outline-only aesthetic)
Sizes
                  * Navigation arrows: 16px (matches label-caps height)
                  * Section arrows: 16px–20px inline with text
                  * Close buttons: 18px text (✕)
                  * Decorative slashes (/): Text size matching body
                  * Menu icon (SVG): 20×14px with 1.5px stroke
Placement
                  * Arrows appear after text (readability flow: text → arrow)
                  * Close buttons appear top-right of drawers/modals
                  * Decorative slashes prefix list items (insights, features)
                  * Nav arrows appear inline with navigation links
Spacing
                  * Icons have 8px–16px gap from associated text (using flex gap utilities)
                  * Never let icons touch text directly
Color
                  * Icons use the same color as surrounding text (Ink at current opacity)
                  * No icon-specific colors
                  * Hover states: icons inherit parent hover opacity
Interaction States
                  * Default: Same opacity as associated text
                  * Hover: Opacity shifts with parent container (e.g., 50% on hover)
                  * Active: Full opacity, no transform
Decorative vs. Functional Icons
                  * Decorative: Ghost markers (text at 5% opacity), atmospheric text
                  * Functional: Navigation arrows, close buttons, menu icon
                  * No decorative geometric icons, illustrations, or emoji-like elements

11. Component Language
Instead of cataloging isolated components, this section documents the construction rules that apply across all component types.
Universal Component Rules
                  * All components sit on 0px radius containers unless specifically part of the "device" or "UI" family
                  * Borders are hairline (1px, 10% opacity) unless the component is a stat card or emphasis element
                  * Internal padding is generous: minimum 24px, typically 32px–40px
                  * No solid fill backgrounds except Stone for device placeholders or Ink for dramatic dark sections
                  * All interactive components have a hover state that changes opacity or reveals an underline

Buttons
Anatomy Buttons in this system are text-first. There are no filled buttons, no primary/secondary color distinctions, and no shadowed buttons.
Variants
                  1. Text link: Plain text with animated underline on hover
                  * border-bottom: 1px solid transparent → border-bottom: 1px solid var(--ink)
                  * Or underline via ::after pseudo-element with transform: scaleX(0→1)
                  2. Labeled action: Text + arrow
                  * "Voltar ao início" with right arrow
                  * "← Voltar" with left arrow
                  * Arrow and text share baseline
                  3. Capsule/Chip: Used only in the view switcher
                  * Pill shape (radius-full)
                  * Padding: 8px 16px
                  * Active state: inverted colors (Ink bg, Page-bg text)
                  * Inactive state: transparent
Proportions
                  * Minimum touch target: 44px height
                  * Padding: 16px horizontal for text buttons
                  * Font: Instrument Sans 13px–14px or label-caps 10px
Interaction
                  * Hover: Opacity 0.5 OR underline reveal
                  * Active: Full opacity, underline visible
                  * No pressed-state color change
                  * No focus ring (system relies on cursor/keyboard context)
Visual Rules
                  * Never use solid color fills
                  * Never use border-radius larger than 4px (except pill switcher)
                  * Never use drop shadows
                  * Never use all-caps for sentence-length buttons (label-caps only for short labels)

Inputs
Anatomy Inputs are extremely rare in this portfolio system. When they appear (contact forms, search), they follow these rules:
Construction
                  * Border: 1px solid hairline (10% opacity Ink)
                  * Background: Transparent or Page-bg
                  * Border-radius: 0px
                  * Padding: 12px 16px
                  * Font: Instrument Sans 13px
Interaction
                  * Focus: Border color transitions to Ink at 30% opacity
                  * No focus glow or outline offset
                  * Placeholder text: Ink at 30% opacity

12. Interaction States
Hover
Text links
                  * Opacity: 100% → 50%
                  * OR underline reveals via transform: scaleX(0→1)
                  * Transition: 0.3s ease or 0.4s cubic-bezier(0.2, 0, 0.2, 1)
Project dots
                  * Dot scales: 1→1.6
                  * Ring expands and fades (Sage border, scale 1→4, opacity 1→0)
                  * Tooltip slides in from left (translateX 10px→0, opacity 0→1)
                  * Duration: 0.3s–0.6s ease-out
Project list rows
                  * Hovered row: opacity 100%
                  * Sibling rows: opacity 40%
                  * Transition: 0.3s ease
Images
                  * Scale: 1→1.02 (subtle)
                  * Shadow: None (shadow is not used)
                  * Transition: 0.6s ease
Pressed / Active
                  * No distinct pressed state beyond hover
                  * Active nav link shows persistent underline
                  * Scale transforms on modals/drawers are the primary "pressed" feedback
Focus
                  * No visible focus rings (system assumes mouse/touch primary input)
                  * For accessibility: focus states should mirror hover states (underline reveal or opacity shift)
                  * Focus-visible: Use outline: 1px solid var(--sage); outline-offset: 4px for keyboard navigation only
Selected
                  * Nav items: Persistent underline
                  * Tabs: Inverted background (Page-bg on Ink container)
                  * Drawers/modals: Visible on viewport
Disabled
                  * Opacity: 30%
                  * Pointer-events: none
                  * No cursor change
Loading
                  * No skeleton screens in this system
                  * Placeholders use Stone backgrounds with centered label text
                  * Loading is communicated through the transition system (scale + fade)
Empty
                  * Empty states use Stone background + centered label-caps at 20% opacity
                  * Never use illustrations for empty states
Success
                  * Success is communicated through Sage accent (stat borders, checkmarks)
                  * No green fills or success banners
Destructive
                  * Destructive actions are extremely rare
                  * When needed: muted red tone, never aggressive
                  * Error messages in the Jornada use red-200 borders and red-500 text at small sizes only
How State Changes Are Communicated
The system prioritizes motion over color for state changes:
                  * Opacity transitions for hover/disabled
                  * Scale transforms for opening/closing
                  * Translate transforms for sliding drawers
                  * Filter blur for background dimming
                  * Never use color fills to indicate state

13. Motion Language
Animation Philosophy
Motion serves functional disclosure, not delight. Every animation answers the question: "Where did this come from, and where is it going?" The motion language is characterized by:
                  * Smooth deceleration (ease-out curves)
                  * Scale-and-fade over slide-and-bounce
                  * Background blur as a depth signal
                  * Never gratuitous or decorative motion
Durations
                  * Micro-interactions (hover, underline, dot pulse): 0.3s
                  * Component transitions (drawers, modals, tooltips): 0.4s–0.6s
                  * Page transitions (case study overlay): 0.6s
                  * Atmospheric motion (ghost markers, scroll reveals): 0.6s–1.0s
Easing
The canonical easing is cubic-bezier(0.2, 0, 0.2, 1). This is used for:
                  * Drawer slides
                  * Modal scales
                  * Case overlay fades
                  * Background blur transitions
This easing creates a smooth deceleration that feels "calm" — it never snaps or bounces.
Transitions
Hover Animations
                  * Underline scaleX: transform: scaleX(0→1); transition: transform 0.4s cubic-bezier(0.2, 0, 0.2, 1)
                  * Opacity shifts: transition: opacity 0.3s ease
                  * Dot ring expansion: animation: ring-expand 0.6s ease-out forwards
                  * Image scale: transition: transform 0.6s cubic-bezier(0.2, 0, 0.2, 1)
Modal Transitions
                  * Scale: 0.95 → 1.0
                  * Opacity: 0 → 1
                  * Duration: 0.6s
                  * Background: Main content scale(0.95) blur(4px)
Drawer Transitions
                  * TranslateX: -100% → 0 (left) or 100% → 0 (right)
                  * Duration: 0.6s
                  * Background: Main content translateX(±100px) scale(0.95) blur(4px)
Page Transitions (Case Study Overlay)
                  * Case overlay: opacity 0→1, scale 0.98→1
                  * Homepage behind: scale 1→0.96, blur 0→2px
                  * Duration: 0.6s
                  * Easing: cubic-bezier(0.2, 0, 0.2, 1)
Micro-interactions
                  * Project dot pulse (mobile): animation: mobile-pulse 2.5s infinite
                  * Scale: 1→1.4→1
                  * Opacity: 1→0.6→1
                  * Ring expansion (desktop hover): Scale 1→4, opacity 1→0
What Kinds of Motion Should Never Be Used
                  * Bounce/elastic easing: Never use bounces, overshoots, or spring physics
                  * Rotation: Never rotate elements (except text orientation for vertical labels)
                  * Parallax: No scroll-driven parallax on content
                  * Ambient motion: No floating, drifting, or continuously moving elements (except mobile dot pulse)
                  * Slide-up entrances: Content does not slide up on scroll reveal; it fades in place
                  * Staggered lists: List items do not stagger-animate in; they appear together
                  * Complex multi-step animations: Single-property transitions only (opacity, transform, filter)

16. Accessibility
Contrast
                  * Primary text (Ink on Page-bg): ~14:1 ratio (exceeds WCAG AAA)
                  * Secondary text (60% opacity): ~8:1 ratio (meets WCAG AA)
                  * Tertiary text (30%–40% opacity): ~4:1 ratio (acceptable for non-essential text)
                  * Sage on Page-bg: ~3:1 ratio (used only for large text or decorative borders, not small body)
Touch Targets
                  * Minimum touch target: 44×44px
                  * Project dots: 8px visible dot inside 44px invisible touchbox
                  * Navigation links: 40px apart (exceeds 44px when including text height)
                  * Drawer close buttons: 44px×44px minimum
Keyboard Navigation
                  * All interactive elements must be focusable
                  * Escape key closes drawers, modals, and overlays
                  * Focus states should mirror hover states (underline reveal or opacity shift)
                  * Tab order: Logical visual order (header left-to-right, then main content top-to-bottom)
Focus Visibility
                  * No default browser outline (system removes outlines for mouse users)
                  * focus-visible should apply:
                  * outline: 1px solid var(--sage)
                  * outline-offset: 4px
                  * For keyboard users only
Readability
                  * Line height minimum: 1.5 for body text
                  * Line length maximum: 65 characters (enforced via max-width containers)
                  * Font size minimum: 12px for readable text, 10px for labels only
                  * Anti-aliasing enabled globally
Responsiveness
                  * Desktop-first design that gracefully collapses:
                  * Asymmetric grids collapse to single column
                  * Horizontal nav becomes horizontal stack on mobile (not hamburger)
                  * Side labels disappear or inline
                  * Artifact scene resizes to portrait
                  * Touch interactions replace hover on mobile (dot pulse animation instead of tooltip)

17. Implicit Cohesion Rules
This section documents the hidden rules that make the system feel unified. These are never explicitly written in a style guide but are consistently followed throughout every artifact.
Typography Carries Hierarchy Instead of Color
The system never uses color to indicate importance. A headline is larger and in Fraunces italic; a label is smaller and in uppercase. Color is reserved for atmosphere (Sage) and readability (Ink), never for competitive emphasis.
Whitespace is Preferred Over Separators
When two sections need distinction, the first tool is 128px+ of vertical space. A hairline border is only used when the content itself is dense and requires explicit grouping.
Interactive Elements Avoid Visual Noise
Buttons have no fill. Links have no background. Cards have no shadow. The interactive state is communicated through motion (underline, opacity, scale) rather than adding visual elements.
Actions Remain Visually Quiet Until Needed
The section navigation at the bottom-left is a 20px icon at 30% opacity. It only reveals its full menu on hover. The project dots are 8px black circles. They only reveal project names on hover. The interface never broadcasts its affordances loudly.
Opacity is the Primary State Mechanism
Instead of changing colors for hover states, the system changes opacity. A link at 100% becomes 50% on hover. A list item at 100% becomes 40% when a sibling is hovered. This maintains hue consistency while creating clear states.
Editorial Asymmetry Creates Interest
The 12-column grid is rarely used symmetrically. Labels occupy columns 1–3 while content starts at column 5. This intentional imbalance mimics editorial magazine layouts and prevents the boredom of centered content.
Ghost Text Provides Atmospheric Depth
Large, low-opacity text (120px at 5%) floats behind content as a section marker. It serves no functional purpose but provides spatial orientation and visual texture without adding noise.
Hairlines Are Structural, Not Decorative
Every border is 1px at 10% opacity. This consistent treatment means borders are felt as structure rather than seen as decoration. The eye perceives the separation without being distracted by the line.
Scale Transitions Replace Color Transitions
When something becomes active, it scales (0.98→1.0). When something is hovered, it may scale subtly. Scale is the primary transform property; color is almost never animated.
The Background Always Stays Warm
Even overlays, modals, and backdrops use the warm Page-bg (#F5F2F0) rather than pure white or dark gray. This maintains the emotional warmth of the interface even when layered.
Device Mockups Are Always Neutral
When showing UI work, device frames use Stone backgrounds with placeholder text. Never use realistic device frames (no iPhone bezels, no MacBook frames). The work is shown as abstract rectangles to maintain focus on the interface, not the device.
Metrics Are Humanized
Numbers are presented in Fraunces (the human font) rather than a monospace or technical font. Even data points feel editorial.
Quotes Are Always Italic and Bordered
Pull quotes use Fraunces italic with a 2px Sage left border. This is the system's only consistent use of color for text emphasis.
Navigation is Always Understated
Whether in the header, a drawer, or a fixed menu, navigation never competes with content. It is always 10px uppercase, widely tracked, and low-contrast until interacted with.
Success and Failure Are Treated With Equal Restraint
In the journey map, pain points use red-200 borders and red-500 text at small sizes. Success metrics use Sage. Neither shouts. Both are small, label-like treatments.
No Component Has a Drop Shadow (Except One)
The entire system avoids elevation through shadow. The only exception is the contact modal, which uses a very diffuse shadow (0 40px 80px rgba(0,0,0,0.1)) to signal that it is a temporary interruption.
The System Never Uses Illustrations
There are no icons, illustrations, patterns, or decorative graphics beyond typography and the artifact scene. Every visual element must justify its existence functionally.
Time is Displayed as Context, Not a Clock
The "7:45pm — Arujá, SP" text at the bottom-left is atmospheric context, not a functional clock widget. It uses the smallest text size and lowest opacity.
Content is Left-Aligned Except in Explicit Centering Moments
Almost all text is left-aligned. Centering is reserved for: ghost markers, empty placeholder states, and the contact modal. This creates a strong vertical rhythm on the left side of the viewport.

18. Dos and Don'ts
DOs
                  1. DO use Fraunces italic for all display headlines and project titles.

                  8. DO use 1px borders at 10% opacity (rgba(26,26,26,0.1)) for all containers and dividers.

                  10. DO use generous whitespace (minimum 80px) between distinct sections.
                  11. DO use asymmetric 12-column grids for case study layouts.

                  13. DO use the custom cubic-bezier(0.2, 0, 0.2, 1) for all major transitions.
                  14. DO use scale and opacity for hover states rather than color changes.
                  15. DO use backdrop-filter blur(10px–12px) for overlays and fixed headers.
                  16. DO use 44px minimum touch targets for all interactive elements.
                  17. DO use Stone (#E6E2DF) for placeholder backgrounds and device mockups.
                  18. DO use ghost markers (120px at 5% opacity) for section atmosphere.
                  19. DO use pull quotes with Fraunces italic and 2px Sage left border.
                  20. DO use scaleX underline animation for navigation hover states.
                  21. DO use max-width 900px for case study reading content.
                  22. DO use sticky positioning for side labels in longform content.
                  23. DO use the 8px base grid for spacing consistency.
                  24. DO use device mockups with exact aspect ratios (totem 16:9, mobile 9:19.5).
                  25. DO use text-only buttons with animated underlines.
                  26. DO use group-hover opacity effects for list items (hovered item 100%, siblings 40%).

DON'Ts
                  1. DON'T use pure white (#FFFFFF) for any background.
                  2. DON'T use pure black (#000000) for any text.
                  3. DON'T use more than two font families in any single view.
                  4. DON'T use bold font weights (700+) anywhere in the interface.
                  5. DON'T use all-caps for headlines or body text (label-caps utility only).
                  6. DON'T use center alignment for longform text or case study content.
                  7. DON'T use colored backgrounds for cards or sections (Stone or transparent only).
                  8. DON'T use drop shadows on cards, buttons, or containers.
                  9. DON'T use gradient backgrounds anywhere.
                  10. DON'T use rounded corners larger than 4px on content elements.
                  11. DON'T use illustrations, icons, or decorative graphics.
                  12. DON'T use saturated colors other than Sage.
                  13. DON'T use bounce, elastic, or spring animations.
                  14. DON'T use skeleton screens or loading spinners (use Stone placeholders).
                  15. DON'T use hover effects that change background colors.
                  16. DON'T use zebra striping in tables.
                  17. DON'T use default browser bullets or numbering (use custom prefixes).
                  18. DON'T use hamburger menu icons (use text nav or SVG line icons).
                  19. DON'T use sticky headers with solid backgrounds (use blur + semi-transparency).
                  20. DON'T use more than 10% Sage in any single viewport.
                  21. DON'T use buttons with solid color fills.
                  22. DON'T use underlines on static text (only interactive links).
                  23. DON'T use parallax scrolling or scroll-driven animations.
                  24. DON'T use floating ambient motion (drifting elements).
                  25. DON'T use staggered list entrance animations.
                  26. DON'T use dark overlays or black backdrops for modals.

                  28. DON'T use checkboxes, radio buttons, or form controls in portfolio content.

19. Implementation Checklist
Before generating any new UI for this system, verify the following:
Product Cohesion
                  * Does this screen feel like it belongs in a gallery/credentialing context, not a marketing or dashboard context?
                  * Is the emotional tone quiet, confident, and restrained?
                  * Would a hiring manager see this as evidence of taste and judgment?
Typography
                  * Are all headlines in Fraunces italic (300 weight)?
                  * Are all functional/UI elements in Instrument Sans (400–500 weight)?
                  * Are section labels in label-caps format (10px uppercase, 0.1em tracking)?
                  * Is there a clear typographic hierarchy without relying on color?
                  * Is the maximum headline size appropriate (32px–84px)?
                  * Is body text minimum 12px and line-height minimum 1.5?
Spacing
                  * Is there at least 80px vertical space between distinct thematic sections?
                  * Are page gutters at least 60px on desktop and 24px on mobile?
                  * Is internal component padding at least 24px (preferably 32px)?
                  * Does whitespace create the primary grouping, not borders?
Layout
                  * Is content left-aligned by default?
                  * Are asymmetric grids used for editorial interest (not centered)?
                  * Is the reading measure constrained (max-width 900px for longform)?
                  * Are sticky labels offset from main content?
Color
                  * Is the background #F5F2F0 (never pure white)?
                  * Is text #1A1A1A (never pure black)?
                  * Is Sage the only accent color used?
                  * Is color used for less than 10% of the viewport area?
                  * Are borders hairline (1px, 10% opacity)?
                  * Is hierarchy created through opacity, not color variation?
Components
                  * Are buttons text-only (no fills)?
                  * Are cards sharp-edged (0px radius) with hairline borders?
                  * Are device mockups abstract (no realistic frames)?
                  * Are interactive elements quiet until hovered/activated?
                  * Is the touch target at least 44px for all interactive elements?
Motion
                  * Are transitions using cubic-bezier(0.2, 0, 0.2, 1)?
                  * Are major transitions 0.6s and micro-interactions 0.3s?
                  * Is scale/opacity/blur used instead of color changes for state?
                  * Are there no bounce, elastic, or decorative animations?
Restraint
                  * Are there no illustrations, icons, or decorative graphics?
                  * Are there no drop shadows?
                  * Are there no gradient backgrounds?
                  * Are there no social proof badges or counters?
                  * Is every element justified by function, not decoration?
Atmosphere
                  * Does the interface feel calm when viewed at full screen?
                  * Is there breathing room around every major element?
                  * Do ghost markers or atmospheric text provide depth without noise?
                  * Does the warm background color maintain consistency across layers?
Accessibility
                  * Is text contrast at least WCAG AA for all readable content?
                  * Are focus states visible for keyboard navigation?
                  * Does the mobile layout maintain touch target sizes?
                  * Is the tab order logical and visible?
